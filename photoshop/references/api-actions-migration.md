# Actions Migration (part 1)

> Adobe Photoshop reference. Original prose; identifiers preserved verbatim.

Use this guide when moving from v1 Photoshop action endpoints to the unified `/v2/execute-actions` endpoint.

## Overview

v1 distributed Photoshop actions across several endpoints. v2 brings the action-based surfaces together under `/v2/execute-actions`; the covered areas include:

- Traditional Photoshop action files using `.atn`
- Inline ActionJSON actions
- Convenience APIs: productCrop, depthBlur, text
- UXP scripts, with limited availability

The consolidated v1 endpoints are:

| v1 Endpoint | v2 Equivalent |
| --- | --- |
| `/pie/psdService/photoshopActions` | `/v2/execute-actions` with `.atn` files |
| `/pie/psdService/actionJSON` | `/v2/execute-actions` with inline actionJSON |
| `/pie/psdService/productCrop` | `/v2/execute-actions` with published action |
| `/pie/psdService/depthBlur` | ⚠️ Not yet supported (Neural Filters unavailable) |
| `/pie/psdService/text` | `/v2/execute-actions` with inline actionJSON or UXP scripts |

## Benefits of the unified endpoint

- **Single Integration Point:** One endpoint handles every action-based workflow.
- **Multiple Actions:** Run several actions sequentially.
- **Additional Resources:** Attach brushes, patterns, fonts, and extra images as references.
- **Published Actions:** Use action files that were previously server-side.
- **Script-Based Outputs:** Capture files generated by UXP scripts with `scriptOutputPattern`.

## Traditional Photoshop actions

### Using .atn files

**Key Differences:**

- Inputs now use `image.source.url` instead of the older `inputs[].href`
- Action references now live at `options.actions[].source.url` rather than `options.actions[].href`
- Outputs write the target URL inside a `destination` object
- The media field is now named `mediaType`, replacing `type`
- For external presigned URLs, `storageType` can be omitted; Azure or Dropbox sources still require it

**V1 request example:**

```shell
curl -X POST \
  https://image.adobe.io/pie/psdService/photoshopActions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "inputs": [
    {
      "href": "<SIGNED_GET_URL>",
      "storage": "external"
    }
  ],
  "options": {
    "actions": [
      {
        "href": "<ACTION_FILE_URL>",
        "storage": "external"
      }
    ]
  },
  "outputs": [
    {
      "href": "<SIGNED_POST_URL>",
      "storage": "external",
      "type": "image/vnd.adobe.photoshop"
    }
  ]
}'
```

**V2 request example:**

```shell
curl -X POST \
  https://photoshop-api.adobe.io/v2/execute-actions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "image": {
    "source": {
      "url": "<SIGNED_GET_URL>"
    }
  },
  "options": {
    "actions": [
      {
        "source": {
          "url": "<ACTION_FILE_URL>"
        }
      }
    ]
  },
  "outputs": [
    {
      "destination": {
        "url": "<SIGNED_POST_URL>"
      },
      "mediaType": "image/vnd.adobe.photoshop"
    }
  ]
}'
```

### Executing a specific action by name

For an `.atn` file that bundles several named actions, set the optional `actionName` field when only one action should run. Without that field, the file's actions run sequentially from start to finish.

```shell
curl -X POST \
  https://photoshop-api.adobe.io/v2/execute-actions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "image": {
    "source": {
      "url": "<SIGNED_GET_URL>"
    }
  },
  "options": {
    "actions": [
      {
        "source": {
          "url": "<ACTION_FILE_URL>"
        },
        "actionName": "<ACTION_NAME>"
      }
    ]
  },
  "outputs": [
    {
      "destination": {
        "url": "<SIGNED_POST_URL>"
      },
      "mediaType": "image/vnd.adobe.photoshop"
    }
  ]
}'
```

A single request may combine named actions with files that should run in full. The action array determines execution order:

```json
{
  "options": {
    "actions": [
      {
        "source": {
          "url": "<ACTION_FILE_URL>"
        },
        "actionName": "Resize to Web"
      },
      {
        "source": {
          "url": "<SECOND_ACTION_FILE_URL>"
        }
      }
    ]
  }
}
```

Here, the first file contributes only `"Resize to Web"`, and the second file contributes every action it contains.

Use `actionName` mainly with `.atn` files that contain multiple named actions. Inline actionJSON already states the exact operation set to execute.


## Using inline ActionJSON

**Key Differences:**

- ActionJSON now appears as inline `content` within the action source
- Include `contentType: "application/json"` with the inline source
- Provide ActionJSON as stringified JSON
- Aside from the inline content, the remaining structure matches the `.atn` pattern

**V1 request example:**

```shell
curl -X POST \
  https://image.adobe.io/pie/psdService/actionJSON \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "inputs": [
    {
      "href": "<SIGNED_GET_URL>",
      "storage": "external"
    }
  ],
  "options": {
    "actionJSON": [
      {
        "_obj": "convertMode",
        "to": {
          "_enum": "colorSpaceMode",
          "_value": "grayscale"
        }
      }
    ]
  },
  "outputs": [
    {
      "href": "<SIGNED_POST_URL>",
      "storage": "external",
      "type": "image/jpeg"
    }
  ]
}'
```

**V2 request example:**

```shell
curl -X POST \
  https://photoshop-api.adobe.io/v2/execute-actions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "image": {
    "source": {
      "url": "<SIGNED_GET_URL>"
    }
  },
  "options": {
    "actions": [
      {
        "source": {
          "content": "[{\"_obj\":\"convertMode\",\"to\":{\"_enum\":\"colorSpaceMode\",\"_value\":\"grayscale\"}}]",
          "contentType": "application/json"
        }
      }
    ]
  },
  "outputs": [
    {
      "destination": {
        "url": "<SIGNED_POST_URL>"
      },
      "mediaType": "image/jpeg"
    }
  ]
}'
```

## Additional contents in actions

ActionJSON may point at additional contents through placeholders. This pattern helps when an action must composite several assets or refer to more than one content item.

**How It Works:**

1. Put the extra items in the `options.additionalContents` array. Each request supports a maximum of 25 additional contents.
2. In ActionJSON, refer to those entries with `__ADDITIONAL_CONTENTS_PATH_0__`, `__ADDITIONAL_CONTENTS_PATH_1__`, etc.
3. Each placeholder's number maps to the same 0-based position in the array.

**Example:**

```shell
curl -X POST \
  https://photoshop-api.adobe.io/v2/execute-actions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "image": {
    "source": {
      "url": "<BASE_IMAGE_URL>"
    }
  },
  "options": {
    "additionalContents": [
      {
        "source": {
          "url": "<OVERLAY_IMAGE_URL>"
        }
      },
      {
        "source": {
          "url": "<BACKGROUND_IMAGE_URL>"
        }
      }
    ],
    "actions": [
      {
        "source": {
          "content": "[{\"_obj\":\"placeEvent\",\"null\":{\"_path\":\"__ADDITIONAL_CONTENTS_PATH_0__\",\"_kind\":\"local\"}}]",
          "contentType": "application/json"
        }
      }
    ]
  },
  "outputs": [
    {
      "destination": {
        "url": "<SIGNED_POST_URL>"
      },
      "mediaType": "image/jpeg"
    }
  ]
}'
```

## Inline content usage

The `/v2/execute-actions` endpoint accepts inline content, meaning content embedded directly in the request, for **text-based resources only**. Correct API usage depends on knowing which resource categories allow that form.

**Payload Size Limits:**

Restrict inline content to 50 KB for an individual resource, and keep the full request payload under 1 MB. When resources are larger, including scripts, actions, or images, place them in external storage and reference them with presigned URLs.

### Inline-supported resources: Actions and UXP scripts

These resource categories can be sent inline:

- **ActionJSON** - Inline JSON definitions for actions
- **UXP Scripts** - Inline JavaScript source

**Inline ActionJSON example**

```json
{
  "options": {
    "actions": [
      {
        "source": {
          "content": "[{\"_obj\":\"gaussianBlur\",\"radius\":{\"_unit\":\"pixelsUnit\",\"_value\":5}}]",
          "contentType": "application/json"
        }
      }
    ]
  }
}
```

Note: Place **stringified JSON** in the `content` field; do not pass a JSON object or array directly. Convert the ActionJSON array to a string with `JSON.stringify()`.

**Inline UXP Script example**

```json
{
  "options": {
    "uxp": {
      "source": {
        "content": "const doc = app.activeDocument; doc.flatten();",
        "contentType": "application/javascript"
      }
    }
  }
}
```

### Not supported: Binary resources

Inline content **is NOT allowed** for:

- **Images** - Main input image or additional images
- **Brushes** - `.abr` brush files
- **Patterns** - `.pat` pattern files
- **Fonts** - Font files

Provide these binary resources as external file references through:

- `url` - External-storage presigned URL
- `creativeCloudPath` - Path in Adobe Creative Cloud storage
- `creativeCloudFileId` - Identifier for a Creative Cloud file
- `lightroomPath` - Adobe Lightroom path, images only

**External reference example**

```json
{
  "image": {
    "source": {
      "url": "<SIGNED_IMAGE_URL>"
    }
  },
  "options": {
    "additionalContents": [
      {
        "source": {
          "url": "<ADDITIONAL_IMAGE_URL>"
        }
      }
    ],
    "brushes": [
      {
        "source": {
          "url": "<BRUSH_FILE_URL>"
        }
      }
    ],
    "patterns": [
      {
        "source": {
          "url": "<PATTERN_FILE_URL>"
        }
      }
    ]
  }
}
```

**Unsupported inline-content example**

```json
{
  "options": {
    "brushes": [
      {
        "content": "base64_encoded_data..." // NOT SUPPORTED
      }
    ]
  }
}
```

Using inline content for binary resources such as images, brushes, patterns, or fonts causes validation to fail. Always provide those resource types by external file reference.

## Script-based output discovery

For UXP scripts that create files, set `scriptOutputPattern` to identify which generated files should be returned as outputs. The parameter can use an exact filename or a glob pattern when outputs are discovered dynamically.

**Supported Destination Types:**

`scriptOutputPattern` applies only to `embedded` and `hosted` destinations. Script-created outputs cannot target external storage such as presigned URLs, Dropbox, or Azure.

**Single-file output example:**

```json
{
  "outputs": [
    {
      "destination": {
        "validityPeriod": 3600
      },
      "mediaType": "image/jpeg",
      "scriptOutputPattern": "final_composite.jpg"
    }
  ]
}
```

**Glob-pattern output example:**

```json
{
  "outputs": [
    {
      "destination": {
        "embedded": "json"
      },
      "mediaType": "application/json",
      "scriptOutputPattern": "*.json"
    },
    {
      "destination": {
        "validityPeriod": 3600
      },
      "mediaType": "image/png",
      "scriptOutputPattern": "result-*.png"
    }
  ]
}
```

**How It Works:**

1. UXP scripts write generated files into the plugin temporary directory
2. The system evaluates files against the pattern and then filters by `mediaType`
3. Every matching file is represented as its own output entry
4. The files are uploaded to the requested destination

**Glob Pattern Examples:**

- `output.json` - Matches a single named file
- `*.json` - Matches every JSON file
- `result-*.png` - Covers result-1.png, result-2.png, etc.
- `layer-[0-9].jpg` - Covers layer-0.jpg through layer-9.jpg

When `scriptOutputPattern` is present, settings such as quality, compression, width, and height do not apply. The service takes files unchanged from the script output directory. Prefer simple patterns and standard glob syntax, for example `*.json`, `result-*.png`, or `layer-[0-9].jpg`.

## UXP scripts (limited availability)

UXP scripts enable modern JavaScript automation. This section applies only to approved users.

### UXP Script Basics

Provide a UXP script either as an external `.psjs` (Photoshop JavaScript) file or as inline content:

**External UXP script source:**

```json
{
  "options": {
    "uxp": {
      "source": {
        "url": "<UXP_SCRIPT_URL>"
      }
    }
  }
}
```

**Inline UXP script source:**

```json
{
  "options": {
    "uxp": {
      "source": {
        "content": "const app = require('photoshop').app; app.activeDocument.flatten();",
        "contentType": "application/javascript"
      }
    }
  }
}
```

### UXP output configuration

UXP scripts are restricted to the UXP plugin temporary directory:

**Mechanics:**

1. **Plugin Temp Directory Writes:**

   - In the UXP script, write with the literal path `plugin-temp:/filename.ext`
   - The UXP module's `storage.localFileSystem` object can also open the plugin temporary directory
   - `plugin-temp:/` is mapped automatically to the correct temporary directory

2. **Specify Output Pattern:**

   - In the output configuration, set `scriptOutputPattern` to select the files to capture
   - Use exact filenames such as `"result.json"` or glob patterns such as `"*.png"` and `"layer-*.jpg"`
   - Captured outputs must match both the pattern and `mediaType`

3. **File Discovery and Upload:**
   - After UXP execution finishes, the worker scans the plugin temp directory
   - It compares files to `scriptOutputPattern` and filters matches by `mediaType`
   - The job result receives one output entry per matched file
   - Upload targets can be `hosted`, `embedded`, or external storage, based on the requested destination

**UXP script example:**

```javascript
const { app } = require("photoshop");
const fs = require("fs");
const path = require("path");

// using plugin-temp: to access plugin temporary directory
const outputFile = "plugin-temp:/generated.json";

async function main() {
  // Generate your output data
  const result = {
    documentName: app.activeDocument.name,
    layers: app.activeDocument.layers.length,
    timestamp: new Date().toISOString(),
  };

  // Save output files to the UXP temp folder
  fs.writeFileSync(outputFile, JSON.stringify(result, null, 2));

  console.log("Output saved to:", outputFile);
}

main().catch((err) => {
  console.error("Error:", err);
  process.exit(1);
});
```

**UXP `scriptOutputPattern` example:**

```shell

  "image": {

      "url": "<SIGNED_GET_URL>"
    }
  },

      "source": {
```

### Additional contents in UXP scripts

Like ActionJSON, UXP scripts can use placeholders for additional contents. That lets scripts access or composite multiple images.

**How It Works:**

1. Place additional contents in `options.additionalContents`
2. In UXP scripts, reference them as `__ADDITIONAL_CONTENTS_PATH_0__`, `__ADDITIONAL_CONTENTS_PATH_1__`, etc.
3. The placeholder number maps to the corresponding 0-based array position
4. Before execution, the worker substitutes those placeholders with actual file paths

**Example:**

```shell
curl -X POST \
  https://photoshop-api.adobe.io/v2/execute-actions \
  -H "Authorization: Bearer $token" \
  -H "x-api-key: $apiKey" \
  -H "Content-Type: application/json" \
  -d '{
  "image": {
    "source": {
      "url": "<BASE_IMAGE_URL>"
    }
  },
  "options": {
    "additionalContents": [
      {
        "source": {
          "url": "<OVERLAY_IMAGE_URL>"
        }
      },
      {
        "source": {
          "url": "<LOGO_IMAGE_URL>"
        }
      }
    ],
    "uxp": {
      "source": {
        "content": "const { app } = require(\"photoshop\"); const fs = require(\"fs\"); async function main() { const overlayPath = \"__ADDITIONAL_CONTENTS_PATH_0__\"; const logoPath = \"__ADDITIONAL_CONTENTS_PATH_1__\"; await app.batchPlay([{ _obj: \"placeEvent\", null: { _path: overlayPath, _kind: \"local\" } }], {}); fs.writeFileSync(\"plugin-temp:/result.json\", JSON.stringify({ overlayUsed: overlayPath, logoUsed: logoPath })); } main();",
        "contentType": "application/javascript"
      }
    }
  },
  "outputs": [
    {
      "destination": {
        "validityPeriod": 3600
      },
      "mediaType": "application/json",
      "scriptOutputPattern": "result.json"
    }
  ]
}'
```

A request can include up to 25 additional contents. Use each content's array index when referencing it from UXP scripts.

**Best Practices for UXP Scripts:**

1. **File Extension:** Use the `.psjs` extension for UXP scripts, identifying them as Photoshop JavaScript rather than general JavaScript files
2. **Output Path:** Save generated outputs under `plugin-temp:/filename`, for example `plugin-temp:/result.json`
3. **Path Handling:** Build file paths with `path.join()`; do not hardcode separators such as `"/"` or `"\\"`
4. **Path Utilities:** Rely on `path.dirname()`, `path.basename()`, and related Node.js path module helpers
5. **Platform-Agnostic:** Keep code free of platform-specific APIs or assumptions for Windows/macOS/Linux
6. **Descriptive Names:** Give output files clear, descriptive filenames
7. **Output Patterns:** Put the desired filename or pattern in the `scriptOutputPattern` parameter
8. **Destinations:** Select `embedded` or hosted storage through `validityPeriod` for destinations; external storage is unavailable for script outputs
9. **Media Types:** Use `mediaType` to filter outputs so only matching file extensions are included
10. **Error Handling:** Make UXP scripts handle errors cleanly
11. **Testing:** Validate scripts thoroughly before production use

Avoid hardcoded file paths and platform-specific separators in UXP scripts. Construct paths with `path.join()`, such as `path.join(outputFolder, "result.json")`, rather than `outputFolder + "/result.json"`. That pattern prevents runtime problems on different operating systems.

## Common migration issues

### Action file not found

❌ **Problem:** v1-style action reference is being used

```json
"actions": [
  {
    "href": "<ACTION_URL>",
    "storage": "external"
  }
]
```

✅ **Solution:** Switch to the v2 `source` shape

```json
"actions": [
  {
    "source": {
      "url": "<ACTION_URL>"
    }
  }
]
```

### Additional contents not working

❌ **Problem:** Placeholder format is incorrect

```json
"content": "[{\"file\":\"additional_contents_path_0\"}]"
```

✅ **Solution:** Use the correct placeholder format

```json
"content": "[{\"file\":\"__ADDITIONAL_CONTENTS_PATH_0__\"}]"
```

### Invalid contentType

❌ **Problem:** Inline content has a missing or incorrect contentType

✅ **Solution:** Always provide contentType with inline content

```json
{
  "source": {
    "content": "...",
    "contentType": "application/json"
  }
}
```

## Validation caveats: stochastic filters

Some Photoshop filter actions rely on an internal random seed, and the V1 and V2 rendering engines do not share the same seed behavior. Because of that, even correctly migrated ActionJSON can produce 50-80% pixel differences from V1 reference output for these filters; treat such differences as noise-pattern variation, not proof of a migration defect. A pixel-diff comparison against V1 output is therefore **not a valid acceptance test** for them.

**Known stochastic filter actions (`_obj` values):** `addNoise`, `grain`, `reticulation`, `mezzotint`, `pointillize`, `clouds`, `differenceClouds`, `spatter`, `sprayedStrokes`, `colorHalftone`

> **Note on `colorHalftone`:** Although the filter is conceptually deterministic, V1 and V2 generate dot patterns and anti-aliasing differently. Correctly migrated ActionJSON may still show roughly 15-20% pixel variation on ordinary images, so validate it as a stochastic case.

**Validation alternatives for stochastic filters:**

- **Histogram comparison** - Check channel mean and standard deviation against an acceptable delta
- **SSIM** - Require Structural Similarity Index to clear a threshold, such as >= 0.85
- **Mean-color comparison** - Evaluate average color by region
- **Status-only validation** - Confirm job success and output-file creation, then skip pixel comparison
