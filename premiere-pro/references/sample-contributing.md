## Contributing

Thanks for contributing.

Use these guidelines when contributing to this project.

### Code Of Conduct

This project follows the Adobe [code of conduct](sample-contributing.md). Participants are expected to honor that code. Send reports of unacceptable behavior to [Grp-opensourceoffice@adobe.com](mailto:Grp-opensourceoffice@adobe.com).

### Have A Question?

Open an issue first. Project committers use issue threads, when suitable, to build agreement on project direction and on solutions for reported issues.

### Contributor License Agreement

Third-party contributions to this project require a signed contributor license agreement. The agreement lets Adobe redistribute your submitted work with the project. Complete the [CLA form](https://opensource.adobe.com/cla.html). If you have already submitted an Adobe CLA, one submission is enough.

### Code Reviews

Submit changes as pull requests so project committers can review them. See [GitHub pull request guide](https://help.github.com/articles/about-pull-requests/) for details about creating pull requests.

When submitting a pull request, follow the [pull request template](sample-contributing.md).

### From Contributor To Committer

Community contributions are welcome. Moving from contributor to committer means joining by invitation, with write access and participation in project decisions. Current committers use an internal nomination flow, and invitations wait until lazy consensus (silence is approval) is reached. Anyone who wants deeper involvement and believes they meet the bar can contact existing committers to discuss it.

### Security Issues

Do not open security reports in this issue tracker. Send them to the security team instead: [submit the report](https://helpx.adobe.com/security/alertus.html).

## Adobe Code of Conduct — Our Pledge

To support a community that is open and welcoming, contributors and maintainers commit to participation in the project and community that is free from harassment for everyone. That commitment includes disability, race, religion, age, body size, ethnicity, nationality, personal appearance, level of experience, gender identity and expression, and sexual identity and orientation.

### Adobe Code of Conduct — Our Standards

Behavior that helps create a positive environment includes:

- Choosing language that feels welcoming and inclusive.
- Respecting different viewpoints and lived experiences.
- Receiving constructive criticism with grace.
- Prioritizing what benefits the community.
- Demonstrating empathy toward other community members.

Participant behavior that is unacceptable includes:

- Sexualized language or imagery, plus unwelcome sexual attention or advances.
- Trolling, insulting or derogatory remarks, and personal or political attacks.
- Harassment in public or private settings.
- Sharing another person's private information, including a physical or electronic address, without explicit permission.
- Any other conduct that could reasonably be viewed as inappropriate in a professional setting.

### Adobe Code of Conduct — Our Responsibilities

Maintainers of the project must explain the standards for acceptable behavior and are expected to respond to unacceptable behavior with corrective action that is fair and appropriate.

They also hold the authority and duty to remove, revise, or decline comments, commits, code, wiki edits, issues, and other contributions when those materials do not align with this Code of Conduct. They may also temporarily or permanently ban a contributor for other conduct they judge inappropriate, threatening, offensive, or harmful.

### Adobe Code of Conduct — Scope

This Code of Conduct governs conduct in project spaces and also applies in public venues whenever someone represents the project or its community. Examples include using an official project e-mail address, posting from an official social media account, or serving as an appointed representative at an online or offline event. Project maintainers may define and clarify further what counts as representation.

### Adobe Code of Conduct — Enforcement

Report abusive, harassing, or otherwise unacceptable behavior to the project team at Grp-opensourceoffice@adobe.com. The team reviews and investigates every complaint, then responds in the way it considers necessary and suitable for the situation. Confidentiality for the person reporting an incident must be protected by the project team. Separate enforcement-policy details may be published elsewhere.

Maintainers who fail to follow or enforce the Code of Conduct in good faith can receive temporary or permanent consequences, as decided by other members of the project's leadership.

## Premiere Pro UXP Samples

These sample plugins show Adobe Premiere Pro workflows built with UXP. Treat them as reference material, adapt pieces in your own projects, or use them to learn the Premiere Pro UXP API surface. See the [Premiere Pro UXP API reference](https://developer.adobe.com/premiere-pro/uxp/).

**New to UXP plugins?** Begin with Adobe's official tutorial, [**Building your first UXP plugin**](https://developer.adobe.com/premiere-pro/uxp/plugins/). It covers creating a plugin scaffold with the UXP Developer Tool and loading that plugin into Premiere Pro. After that, the samples here are easier to navigate.

### Getting started

### 1. Clone the repository

```bash
git clone https://github.com/AdobeDocs/uxp-premiere-pro-samples.git
cd uxp-premiere-pro-samples
```

### 2. Build the sample you want to run

Build expectations vary by sample, including samples that do not require a build step.

**[`premiere-api`](sample-panels.md) — TypeScript; build required**
For complete setup and build steps, use the [`premiere-api` README](sample-panels.md).

**[`metadata-handler`](sample-panels.md) — JavaScript; no build required**
This sample needs no install or build command. Setup details are in the [`metadata-handler` README](sample-panels.md).

**[`oauth-workflow-sample`](sample-panels.md) — JavaScript; uses a local Node.js server**
Before the first run, use the [`oauth-workflow-sample` README](sample-panels.md) to configure credentials and the local server.

### 3. Load the plugin in Premiere Pro

All samples use the same loading sequence:

1. Start Premiere Pro, or start Premiere Pro Beta.
2. Start the UXP Developer Tool.
3. Use **Add Plugin**, then choose the sample's `manifest.json`.
4. Use **Load**, or choose **Load & Watch** when source-file edits should trigger automatic reloads.

Premiere Pro lists the panel at **Window → UXP Plugins**.

### TypeScript support

Official TypeScript declarations for Premiere Pro UXP APIs are delivered through the [`@adobe/premierepro`](https://www.npmjs.com/package/@adobe/premierepro) package. Choose the channel that matches the project:

```bash

### Stable APIs

npm install -D @adobe/premierepro

### Beta APIs (preview of upcoming surface)

npm install -D @adobe/premierepro@beta
```

TypeScript projects load those declarations without extra configuration. For JavaScript projects that need autocomplete and inline documentation inside Visual Studio Code or Cursor, place a `jsconfig.json` at the plugin root:

```json
{
  "compilerOptions": {
    "types": ["@adobe/premierepro"]
  },
  "excludes": ["node_modules"]
}
```

After that, both TypeScript and JavaScript projects surface autocomplete and inline documentation.

### Beta APIs (preview of upcoming surface) — Frequently asked questions

<details>
<summary>**Premiere Pro does not show my plugin.**</summary>

Check these items:

1. Confirm Developer Mode is enabled in Premiere Pro, then restart Premiere Pro after enabling it.
2. Make sure the `host.minVersion` in `manifest.json` is not higher than the installed Premiere Pro version.
3. UDT should show Premiere Pro in its left-hand pane; if it does not, restart both applications.

</details>

<details>
<summary>**Where can I find console.log output?**</summary>

In UDT, select the loaded plugin and click **Debug**. A Chromium DevTools window attaches to the plugin so you can inspect console output, network traffic, and the DOM.

</details>

<details>
<summary>**Do Premiere UXP API calls run asynchronously?**</summary>

Yes. Most Premiere UXP APIs return Promises, so call them with `await` or chain `.then()`. Skipping the wait can produce incorrect results and may block the panel UI. Across its `src/` modules, the `premiere-api` sample consistently uses `async`/`await`, making it the recommended pattern.

</details>

<details>
<summary>**How should file system or network access be requested?**</summary>

Add the needed capabilities under `requiredPermissions` in `manifest.json`:

- The [`oauth-workflow-sample` manifest](https://raw.githubusercontent.com/AdobeDocs/uxp-premiere-pro-samples/main/sample-panels/oauth-workflow-sample/manifest.json) shows `network` and `launchProcess` permissions.
- The [`premiere-api` manifest](https://raw.githubusercontent.com/AdobeDocs/uxp-premiere-pro-samples/main/sample-panels/premiere-api/public/manifest.json) shows `localFileSystem` and `clipboard` permissions.

</details>

<details>
<summary>**UDT does not reload my manifest.json changes.**</summary>

UDT's **Watch** mode reloads source files only. For `manifest.json` changes, use **Unload** and then **Load** in UDT.

</details>

<details>
<summary>**Can a UXP panel be paired with a native C++ plugin?**</summary>

Yes. The official [Hybrid Plugins](https://developer.adobe.com/premiere-pro/uxp/plugins/hybrid-plugins/) guide covers that combination.

</details>

<details>
<summary>**Does documentation exist for Premiere Pro transcript JSON?**</summary>

Yes. This repository includes the full specification at [`sample-panels/premiere-api/assets/transcript_format_spec.json`](https://raw.githubusercontent.com/AdobeDocs/uxp-premiere-pro-samples/main/sample-panels/premiere-api/assets/transcript_format_spec.json).

</details>
